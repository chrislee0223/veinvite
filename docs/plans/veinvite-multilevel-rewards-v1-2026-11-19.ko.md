# VeInvite 신규 5단계 보상·네트워크 시스템 — 공식 설계 기록 (v1)

> **상태: 설계 확정 사항의 누적 기록 / 구현 전 검증 필요 / 운영 배포 승인 아님**  
> 최초 기록: 2026-11-19 (KST)  
> 저장 위치: 별도 계획 브랜치 `plan/multilevel-rewards-2026-11-19`. **`main`과 현재 운영 서비스에는 신규 시스템을 적용하지 않는다.**  
> 목적: 긴 대화에서 합의한 요구사항을 손실 없이 보관하고, 추후 구현·테스트·안전한 전환의 기준으로 사용한다.  
> 이 문서의 구분: **[확정]** 사용자가 명시 승인한 정책 / **[구현·검증]** 결정된 정책에 대한 기술적 안전 요건 / **[미결·외부확인]** 아직 결정·검증되지 않은 사항. 예시는 실제 지급 약속이 아니다.

## 0. 제품 원칙과 배포 안전

- [확정] 목표: 신규 이용자 온보딩뿐 아니라 **온보딩 완료 후 지속적인 VeBetterDAO dApp 활동**까지 장려하는 추천·활성 네트워크 보상.
- [확정] 현재 VeInvite 운영 기능을 직접 갈아엎으면서 개발하지 않는다. 신규 기능은 별도 브랜치·별도 검증 환경에서 준비하여 사용자 승인 후 한 번의 계획된 전환으로 보이게 한다.
- [확정] **신규 보상은 새 정책이 시작된 라운드 이후의 새로운 보상 사건에만 적용**한다(A안). 그 이전 진행·확정·대기 보상과 기존 X 공유 약속은 **원래 정책으로 별도 정산·보호**한다. 과거 보상 소급 변경 금지.
- [확정] 새 시스템에 문제가 생겨도 과거/신규 지급 내역을 잃지 않고 원래 방식으로 복귀할 수 있어야 한다. DB를 과거 날짜로 통째 복원해 신규 사용자·지급 내역을 지우는 복구는 금지.
- [구현·검증] 실서비스 전환은 운영자 명시 승인/정책 버전 스위치로 수행하고, 위험 시 신규 보상 생성만 중지하되 기존의 확정 채무·진행 중 지급은 보호한다.
- [구현·검증] 임의의 특정 VeBetterDAO dApp에 보상이 쏠리도록 미션 대상/투표 대상을 지정하지 않는다.

## 1. 보상 재원 및 종류

### 1.1 80:20 이후 참여자 풀의 60:30:10

- [확정] VeInvite 수령 재원에서 **참여자 80%, 운영 20%**를 구분한다.
- [확정] 아래 60:30:10은 **이미 운영비 20%를 제외한 참여자 풀**을 기준으로 한다. 운영비를 중복 공제하지 않는다.
- [확정] 참여자 풀: **신규 온보딩 60% / 활성 네트워크 30% / 주간 리더 10%**.
- 예: 참여자 풀 1,000 B3TR이면 신규 600 / 활성 300 / 리더 100 B3TR. 사용자가 특정 1명뿐이더라도 *새 규칙에서 1,000 전체가 자동으로 그 1명에게 귀속되는 것은 아님*.

### 1.2 신규 온보딩 (60%)

- [확정] 실제 신규 이용자가 **서로 다른 VeBetterDAO dApp 3개에서 유효한 활동 및 해당 dApp 보상 수령**을 완료하고, **다음 라운드에 투표**까지 마친 경우에만 유효한 최초 온보딩 보상 사건으로 인정한다. **같은 라운드에 dApp 활동과 온보딩 투표를 모두 마칠 수 없는 현재 VeInvite의 2라운드 미션 순서를 유지**한다.
- [확정] 특정 dApp을 지정하지 않는다. 시빌·기존 사용자 재포장·자기 초대·중복 최초 온보딩은 거절한다.
- [확정] 해당 보상 사건의 최대 5단계 상위 추천인에게 아래 단계별 비율로 배분한다.
- [확정] **직접 추천인(1단계)은 그 라운드에 본인이 투표하지 않았더라도** 유효한 최초 온보딩에 대한 70%를 받을 수 있다. 2~5단계는 자격을 충족해야 한다.
- [구현·검증] 최초 신규 이용자 여부를 판단하는 구체적 증빙(기존 VeBetterDAO 참여/VeInvite 과거 완료/지갑 연계 시빌 등)은 실제 온체인 기록과 검증 규칙을 명세화한다.

### 1.3 활성 네트워크 (30%)

- [확정] **온보딩을 이미 완료한 사람만** 이후 라운드부터 활성 보상 발생의 기준 이용자가 된다. **온보딩을 완료한 바로 그 라운드에는 활성 보상을 중복 발생시키지 않는다.**
- [확정] **온보딩 완료 이후의 활성 네트워크** 기준: 해당 라운드에 **VeBetterDAO dApp 1개 이상에서 실제 활동을 완료하고 B3TR 보상 수령까지 확인 + 어떤 VeBetterDAO dApp이든 투표 1회 이상**. 활동한 dApp과 투표 대상 dApp이 같을 필요는 없다. 단순 접속/미보상 활동/투표만으로 활성 요건을 충족했다고 보지 않는다. 이는 **기존 신규 온보딩의 'dApp 활동 라운드 → 다음 라운드 투표' 규칙과 별개**다.
- [확정] 같은 라운드에 활동/투표를 여러 번 해도 **활성 이용자 1명으로 1회**만 인정한다. 투표 횟수에 비례한 추가 배정 없음.
- [확정] 활성 이용자의 **상위 추천인도 같은 라운드에 위 활성 조건을 충족해야** 자기 단계 몫을 받는다(A안). 미활성 추천인 몫을 다른 단계 추천인에게 당겨 나눠주지 않는다.
- [확정] 새 정책 시작 전에 이미 VeInvite를 정상 완료한 기존 사용자들도 **출시 이후의 검증된 활동**부터 활성 보상 발생 대상이다. 과거 활동 소급 지급 없음.
- [구현·검증] dApp 활동 **및 B3TR 보상 수령**, 어떤 dApp이든 유효한 온체인 투표의 증빙과 귀속 라운드, 시빌 검사, 경계 시각을 명확히 검증한다. 신규 온보딩의 라운드 간 순서와 기존 온보딩 완료자의 활성 네트워크 기준을 섞지 않는다.

### 1.4 리더 (10%)

- [확정] 해당 라운드에 **직접 초대한 신규 이용자의 유효한 온보딩 완료 건수**가 가장 많은 추천인이 리더.
- [확정] 공동 1등이면 리더 보상 균등 분배. 해당 라운드에 유효 완료가 없으면 리더 보상 수령인 없음.
- [확정] 리더는 **직접 성과만 계산**하며 2~5단계 하위 네트워크 성공 건수는 리더 순위에 포함하지 않는다.
- [구현·검증] 리더 확정 전 최종 시빌 검증 및 라운드 기준 완료 블록 확인. 확정 지급 후 소급 변경으로 다른 수령인의 정상 지급 내역을 무단 수정하지 않는다.

## 2. 5단계 추천 분배 및 회계

- [확정] **1단계 70% / 2단계 15% / 3단계 8% / 4단계 5% / 5단계 2%**. 적용 대상: 신규 온보딩과 활성 네트워크의 각 보상 사건.
- [확정] 한 사건에 **먼저 배정된 금액 100% 안에서만** 단계별로 나눈다. 1명이 활동한 것을 여러 명의 활동으로 중복 산정하거나 같은 돈을 단계마다 새로 만들어 지급하지 않는다.
- [확정] 상위 단계가 없거나 활동 조건 미충족이면 **그 단계의 몫 100%를 다음 라운드 일반 참여자 보상 풀로 반환**; 동일 사건의 다른 단계에 추가 지급하지 않는다.
- [확정] **범주 전체에 받을 사람이 아예 없을 때**는 미사용 범주 풀의 **50%는 같은 범주에 이월**, **50%는 일반 참여자 풀에 반환**하여 다음 라운드 60:30:10 기준으로 분배한다.
- [확정] 활성 이용자가 아예 없다면 활성 범주 전체 미사용 50:50 규칙. 활성 이용자는 있으나 *상위 추천인이 모두 미활성*이라 지급 불가한 단계 몫은 **100% 일반 풀 반환**한다. 두 규칙을 중복 적용하지 않는다.
- [확정] Claim 만료 미수령금, 조건 미충족 X 공유 10%, 결손 단계 몫도 **100% 일반 풀 반환**.
- [확정] 반환·이월되는 돈은 이미 참여자 몫이므로 **운영비 20% 재공제 금지**. 이전 라운드 미지급/기존 X 채무/지급 진행 중 금액은 반환 대상으로 잘못 분류하지 않는다.
- [구현·검증] B3TR 최소 단위에서 정수로 분배하고 절사 잔여는 명확하게 다음 풀로 이월. 중복 이월·중복 반환·잔액 음수·총 재원 초과 금지.
- [구현·검증] **보상 사건 ID / 수령인 / 단계 / 정책버전 / 라운드**를 원장에 고정 기록하고 같은 사건의 중복 수령·중복 지급을 방지. 두 번 Claim하거나 재시도·서버 장애가 나도 실제 체인 지급은 최대 한 번.

## 3. 초대 슬롯·미션 초기화·재초대·네트워크

### 3.1 동시 초대 2슬롯

- [확정] 초대 슬롯은 **동시에 진행 중인 초대 2개**의 제한이며, 라운드별 또는 평생 총 초대 가능 수 2명이라는 뜻이 아니다.
- [확정] 완료 또는 정상 해제된 슬롯은 재사용되어 같은 라운드에 3건 이상 성공하는 것도 가능하다.
- [구현·검증] DB에 미리 준비된 **2갈래 네트워크(Binary) 정책**과 **동시 초대 슬롯 2개**는 별개이다. 비활성 준비 정책을 실수로 활성화하여 누적 하위 인원을 2명으로 제한하지 않는다.

### 3.2 2라운드 미완료 초기화

- [확정] 첫 도전에서 dApp 체험 창(진입 R) 및 투표 창(R+1)을 지나 **R+2 시작 시 미완료 도전 만료**, 미션 진행 상태를 **0/3부터 새로 시작**한다.
- [확정] 보호금도 만료된 도전에 대해서는 재활용 대상으로 전환한다. **이미 확정/검증 대기/지급 대기인 금액은 무조건 반환하지 않고 보호**한다. 과거 기록은 삭제하지 않는다.
- [확정] 재시작 이후 실제로 수행한 새 dApp 활동/투표만 인정한다. 과거 도전에서 완료한 1~2개 앱이나 옛 투표를 새 도전에 재사용하지 않는다. 하나의 지갑이 최초 온보딩 보상을 중복 발생시키지 않는다.
- [확정] 네트워크 UI에서 별도 '만료/재도전/초기화' 상태를 만들지 않고 **처음 초대한 사람처럼 '온보딩 중'** 및 0/3으로 표기한다.
- [구현·검증] 실제 DB의 재시작 함수는 존재하나 2026-11-19 점검 당시 **`reward_admission_bridge.mission_retry_settings_v1.enabled=false`**, 재시작 이력 0건. 현 운영에서 자동 초기화된다는 뜻이 아니다.
- [구현·검증] 기존 미완료 초대 28건 중 일부는 오래되거나 라운드가 연결되지 않아 별도 전환 점검이 필요하다. 재시작 활성화 전에 예외/과거 보호금/시빌 상태를 검증하고 재시작을 보상 정산과 연동한다.

### 3.3 초대자 해제 및 다른 초대자의 재초대 (A안 확정)

- [확정] 최초 온보딩 **미완료**라면 기존 초대자가 해당 관계를 해제할 수 있고 **초대 슬롯을 복구**한다.
- [확정] 정상적으로 해제된 피초대자는 **다른 초대자의 초대를 새로 받아** 0/3부터 다시 도전할 수 있다.
- [확정] 한 번이라도 **최초 온보딩 완료**한 지갑은 다른 초대로 '신규 이용자'가 되어 보상을 다시 발생시킬 수 없다.
- [확정] 피초대자 B가 미완료인 상태에서 이미 D를 초대했더라도, A가 B를 해제해 C가 B를 재초대하는 경우 **B→D 관계는 그대로 유지**한다. C의 상위 추천인 지위는 **새 관계가 유효하게 확정된 이후의 활동**에만 적용. 기존 확정·지급된 사건의 상위 추천인을 소급 변경하지 않는다.
- [구현·검증] 실 DB의 `invitations`에는 초대받은 지갑 당 전체 이력 1건을 허용하는 고유 제약이 있다. A안 구현 시 이를 무턱대고 삭제하지 말고 **과거 이력 보존 + 동시에 유효한 초대 관계 1개 + 평생 최초 온보딩 최대 1번**을 강제하는 새 이력 구조/제약으로 안전하게 변경해야 한다.
- [구현·검증] 초대 해제와 도전 완료가 동시에 일어날 때 지급·슬롯·네트워크 연결을 원자적으로 판정한다.

### 3.4 네트워크 자격과 상태

- [확정] 기존 하위 관계와 유효한 인연 기록을 보존하고, 최대 **5단계 상위**만 보상 계산에 사용한다. 루프/자가초대/중복 조상/복수 부모가 생기지 않도록 한다.
- [확정] 네트워크 상태는 **활성 / 미투표 / 휴면 / 복귀 / 온보딩 중**. 온보딩 미완료는 휴면이 아니다. **이번 라운드 아직 미투표**를 즉시 휴면으로 확정하지 않는다. 전 라운드 휴면 뒤 이번 라운드 복귀한 사람은 활성에도 해당하므로 집계 중복 방지.
- [확정] 내 아래 전체 네트워크의 인원 현황은 **지갑 기준 고유 인원**으로 센다. 1명이 여러 추천인에게 혜택을 만들어도 활성 이용자는 1명.
- [구현·검증] 첫 유효 초대 관계 변경/복귀 시점, 과거 하위 D가 새 조상 C에게 연결되는 유효 시점 등은 사건별로 확정 기록. 이미 지급 완료된 과거 보상은 재계산하지 않는다.
- [구현·검증] 이용자 증가 시 전체 네트워크 화면을 매번 복잡하게 조회하지 않고 집계·캐시를 효율적으로 사용; 모바일 스크롤·리더보드 등 현재 개선사항을 보존.

## 4. Claim, X 공유, 공지

### 4.1 지급 기한

- [확정] R 라운드에서 성과가 발생하면 라운드 종료 정산 후 **R+1 라운드에 Claim** 가능. **R+2 라운드 시작 시까지 미수령인 보상**은 일반 풀로 반환.
- [확정] 정산/신원·시빌 판정/온체인 지급 처리 중인 금액은 기한이 지났어도 채무를 보호. 수령 최소금액 제한 없음.
- [확정] 신규 온보딩 / 활성 네트워크 / 리더 보상은 **각각 상세·알림·Claim**을 제공. 편의상 '모두 수령' 버튼을 둘 수 있으나 내부 거래 중복 지급 금지.

### 4.2 개별 보상마다 X 공유 90:10 (최종 확정)

- [확정] **보상 종류별 1회가 아니라 보상 발생·수령 건별 개별 공유**를 허용한다. 같은 라운드 신규 온보딩 3건 보상이라면 각 건 별도로 X 공유 기회가 있다. 목적은 게시물 확산.
- [확정] 개별 보상 총액의 **기본 90%를 Claim**, 나머지 **10%는 유효한 X 게시물 게시 및 유지 확인 시 지급**. *추가로 10%를 재원 밖에서 만드는 것이 아니다.*
- [확정] Claim 후 **24시간 내 게시**, 해당 게시물을 **24시간 유지**해야 한다. 보상별 다른 게시물만 인정하며 X 게시물 1개를 여러 보상 건에 중복 재사용하지 않는다.
- [확정] 공유하지 않거나 요건 불충족인 미지급 10%는 일반 풀로 반환. 게시 후 검증 대기 중인 금액은 다음 라운드로 넘어가더라도 보호.
- [확정] X API/서버 오류·일시적 이용량 제한으로 확인이 불가능하다는 이유만으로 정상 보상의 10%를 바로 몰수하지 않는다. 재검증 가능할 때까지 보호, 검증 결과에 따라 지급/반환.
- [구현·검증] 현재 운영 시스템은 **고정 10 B3TR 추가 지급(`x-promotion-additive-v2`)**이다. 새 90:10과 다른 정책. 레거시 고정 지급 약속은 그대로 처리하고 새 정책별 독립된 분배/의무/검증/지급 기록을 둔다.
- [구현·검증] 기존 DB의 X 공유 기회는 초대 코드당 1회 고유 제한이 있어, 새 모델의 **보상 사건별 X 공유**를 옛 구조에 억지로 끼워 넣지 않는다. 서로 다른 게시물·발행자 검증·24시간 보유 확인 및 재시도/장애 복구 테스트.
- [구현·검증] X 스팸/반복 게시 정책과 홍보 표시 요구를 검토하고, 기존 X API 비용 상한(월 약 $5)을 의도치 않게 초과하지 않게 한다. 비용 한도 도달 시 이미 발생한 10% 채무를 임의 소멸시키지 않는다.

### 4.3 UI/알림

- [확정] 홈은 **세로 3개 보상 카드**만 간결하게 배치, 각 카드에 기존 스타일의 ⓘ 상세 팝업. 추가 전체풀 중복 표시와 과도한 문구를 피한다.
- [확정] 신규 온보딩 카드: **직접 초대 1건당 예상 수령 보상**(예: 신규풀 600 / 예상 유효 완료 3명 × 직접 70% = 140). 진행/예상 대상 수에 따라 변동하는 *예상치*.
- [확정] 활성 네트워크 카드: **전체 활성 네트워크 풀**; 리더 카드: **전체 리더 풀**. 둘을 개인 확정 수령액처럼 표시하지 않는다. 홈 예측 카드에 X 공유 금액을 섞지 않는다.
- [확정] X 공유는 Claim 후 적절한 시점에 보상 건마다 안내. 다국어 문구와 레이아웃 유지. 알림 중복/누락 금지.
- [구현·검증] 앱 첫 진입 시 예상 보상 '-' 표시, 지연 로딩, 오래된 예측 로직의 532 B3TR 잔존값 등을 다시 노출하지 않도록 새 단일 계산 기준으로 연결. 기존 모바일 네트워크·리더보드 기능 회귀 테스트.

## 5. 기존 운영과의 실제 충돌 지점 (읽기 전용 점검 기준)

2026-11-19 읽기 전용 연결 점검에서 확인한 항목:

1. 원래 보상 큐는 **초대 코드당 고유 기록 1건**의 구조. 신규 5단계 다수 수령인과 활성 네트워크 반복 성과는 **신규 독립 원장/의무/지급 구조**가 필요.
2. 원래 X 공유 기회는 **초대 코드당 1건**의 제한. 신규 개별 보상 X 공유는 별도 사건 키와 기록 필요.
3. 기존 `invitations`는 **피초대자 지갑당 전체 이력 1건 고유 제약**. 미완료 해제 후 재초대 A안을 위해 변경·이력 보존 설계 필요.
4. 재시작 함수 `read_invitation_mission_retry_state_v1`, `begin_invitation_mission_retry_v1` 존재. 기능은 **현재 비활성**이며 처음부터 새 미션 0/3을 재검증하는 전체 플로우가 필요.
5. 과거 보호금은 '2라운드 이후 전액 자동 반환'이 아니며, 늦게 완료할 여지가 있는 미완료자에 대한 가중 보호와 이미 확정된 채무가 있다. 신규 재시작 규칙과 회계 일치 필요.
6. DB에 비활성 **`binary_balanced_v1` / `max_children=2`** 준비 정책 존재. 이는 현재 초대 슬롯 2개와 같은 제약이 아님.
7. 기준 복구 기록: [GitHub Issue #1345](https://github.com/chrislee0223/veinvite/issues/1345), 코드 기준 `e8183d98669d60e94e30154e5a6f343f3cc786e3` / `backup/pre-multilevel-rewards-2026-11-19`. 이후에도 모바일·리더보드·첫 로딩 개선 코드가 main에 추가됨. **신규 개발은 항상 전환 직전 최신 운영 코드를 기준**으로, 최근 개선을 잃지 않도록 한다.
8. **GitHub 코드 백업은 Supabase 전체 DB 백업이 아니다.** 완전한 DB 스냅샷, 백업 보존, 원장/지급 대기 금액 복구 방법과 실제 롤백 리허설은 아직 미완료.

## 6. 구현·검증 계획 (운영 배포 전 필수)

### 6.1 코드 및 재원

- [구현·검증] 현재 배포 버전과 GitHub 최신 main, 기존 원장·정산 기능을 일치 확인 → 독립 개발 브랜치/격리된 테스트 DB → 신규 스키마/정책 버전별 이중 과금 없는 회계 → 정산 시뮬레이션.
- [구현·검증] **원본 과거 원장 삭제 금지**. 사용하지 않는 옛 계산 호출 경로는 안전한 전환 및 복구 준비 후 격리·정리. 원본 기록, 감사 내역, 기존 지급 의무는 보존한다.
- [구현·검증] 원장 단위로 `초기 참여자 풀 = 실제 지급 + 청구 대기 + 검증 보호 + 범주 이월 + 일반풀 반환 + 정수 잔여` 등 총합 검증. 일부 재분배는 라운드 간 명확한 소유권으로 추적.
- [구현·검증] 실제 검증된 온체인 기록 기준으로 모든 기여·투표·지급을 확인하고, DB와 온체인 상태가 다르면 보상 결정을 보류/재검증.
- [구현·검증] 5단계 그래프에는 순환/자가추천/시빌 클러스터/과거 관계 해제/이전 온보딩/중복 보상 수령 방지.

### 6.2 꼭 재현할 테스트

- 빈 라운드·참여자 1명·참여자 급증·범주별 수령자 0명·단계별 자격 결손·보상 먼지 금액.
- 동일 라운드 다회 투표/여러 dApp 활동 / 최초 온보딩 동일 라운드 활성 중복 방지.
- 상위 5명 중 일부만 활동, 중간 조상 미활성, 여러 자손 겹치는 수혜자.
- 초대 슬롯 2개 가득 참→1건 완료→재초대; R+2 미션 0/3 재시작; 오래된 미완료·라운드 미연결 사례.
- 초대 해제와 완료/시빌 판정 동시 요청, 재초대 후 B→D 하위 관계 보존, 두 상위 추천인의 과거/미래 활동 보상 귀속.
- 라운드 변경 전후 최종 블록, 늦은 온체인 확인, 재시도/DB 장애/중복 Claim/지급 중단 후 재개.
- 신규·활성·리더 보상을 한 사람이 동시에 받는 경우 **각 범주별 독립 재원과 독립 X 공유**가 혼동되지 않는지.
- X 게시 유지 24시간, 늦은 검증, 게시물 삭제/교체/중복 URL/중복 post ID, API 한도·장애.
- 시빌 사후 재분류, 리더 공동 1등, 이미 정산된 보상과 미정산 보상 분리.
- 다국어·PC/모바일 UI·첫 로딩·네트워크 스크롤·초대자 랭킹·알림 시점 회귀.
- 전환 직전 버전 대비 전체 통합 기능/비용/부하 검증, **비파괴적 구버전 복귀 리허설**.

### 6.3 배포 통제와 복구

1. 운영 전 최신 코드·Supabase 데이터/구조·정산 채무·X 공유 보류금·환경 설정의 안전한 백업 및 복구 테스트.
2. 충분한 스테이징/테스트넷 검증, 소규모 실데이터 상당의 시뮬레이션, 운영자 확인.
3. 공개할 정확한 시작 라운드/블록을 **운영 전 확정**하여 경계 전후 사건은 반드시 구·신 정책 하나에만 귀속.
4. 릴리스 시 새 정책 원장과 레거시 지급 흐름 분리하고 비상 정지/모니터링/롤백 기준을 준비.
5. 사고 시 새 보상 적립만 정지; 이미 지급된 체인 거래를 지우거나 DB 전체를 과거 날짜로 복원하지 않는다. 미지급 권리와 기존 공유 채무 정산을 보존.

## 7. 반드시 외부 확인하거나 세부 명세를 마쳐야 할 사항

- **[미결·외부확인: 가장 중요]** VeBetterDAO 공식 Rulebook/Fair Use Rule에서 **온보딩 완료 이후 제3자의 dApp 활동·투표를 기준으로 상위 추천인에게 반복 지급하는 활성 네트워크 30% 보상**이 허용되는지. 특정 dApp 미지정이나 추천인의 추가 투표 요구만으로 자동 면책되지 않는다. 공식 확인 전 운영 배포 판단 금지. 참고: https://docs.vebetterdao.org/developer-guides/rulebook-for-apps / https://vechain.discourse.group/t/vebetterdao-proposal-introduce-fair-use-rule-prevent-dapp-level-redundant-incentive-loops/375
- **[미결·구현세부]** 'dApp 활동 1회'의 정확한 유효 증거/앱 구분 방식과 Vote2Earn 투표 확인 기준, 동일 활동/투표의 재사용 방지.
- **[미결·구현세부]** 기존 미완료/시빌 검사/라운드 미연결자의 초기화 전환 예외 정책과 지급 보류금의 법적·회계적 보호 범위.
- **[미결·릴리스]** 시작 라운드·사용자 안내일, 롤백 책임자/프로세스, API 비용 한도에서 공유 게시 검증 지연 해소 방법.
- 위 항목은 이미 확정한 60:30:10, 70:15:8:5:2 등의 구조를 임의로 재질문하는 근거가 아니다. 운영 안전에 직결되는 사실 확인 또는 기술 세부 명세로 취급한다.
