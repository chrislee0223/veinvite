# VeInvite 공통 보상 풀 전환 — 검증된 구현 순서

## 합의된 지급 정책
- 온체인 앱 **사용자 보상 풀(80%)** 한 곳에서 지급 가능 금액을 판단한다. 이미 분리된 운영 20%를 재차 차감하거나 새로운 운영 준비금을 만들지 않는다.
- 미션을 완료하지 않은 과거/신규 참여자에게는 보상을 미리 예약하지 않는다. 완료 시점에 시빌·최종성·중복 여부를 확인하고 원자적으로 보상액을 산정·확정한다.
- 이미 확정된 미지급 **기본 보상**, 실제 유효한 X 보상 10 B3TR, 회수 오프셋은 보존한다. 원장과 과거 지급기록은 변경하거나 삭제하지 않는다.
- 과거 Source Sweep과 Bank Stress는 **회계상 분류**이지 온체인 풀에 더해진 신규 자금이 아니다. 해제 시 이중으로 풀에 더하지 않는다.
- 라운드 ID는 이력·증빙 연결에 유지하되, 확정되지 않은 라운드별 예산 한도는 새 가격 결정에 적용하지 않는다.

## 1단계: 본 PR — 읽기 전용 계산기
`read_reward_shared_pool_capacity_shadow_v1`을 추가한다. 기록·지급·설정 변경은 하지 않는다.
- `실제 가용 풀 = 온체인 관측 잔액 - 이미 확정된 미지급 기본/X 의무`
- 아직 미지급 의무가 아닌 현재 라운드 잠정 예산은 `outstanding`에서 한 번만 분리한다.
- 계산을 검증하기 위해 1/2/3명 완료 시 수치와 관측 시간만 반환한다. **실제 지급 허가에 사용할 수 없다.**

## 필수 후속 단계 (현행 시스템 간 충돌 방지)
1. **원자적 공통 풀 지급 Writer:** 금융 advisory lock을 유지하고 완료·Sybil CLEAR·원본 배정 영수증·기존 중복 지급·지급 능력을 한 트랜잭션에서 검증한다. 자금 부족 시 확정하지 않고 자동 재시도를 유지한다.
2. **DB 예산 트리거 2곳:** `enforce_reward_queue_cohort_budget`, `validate_reward_x_promotion_split`은 기존 예약에는 그대로 적용, 새로운 공통 풀 알고리즘에만 제한을 조건부로 바꿔야 한다. X 보상 10개는 확정 지급과 별도 회계로 보존한다.
3. **글로벌 일시 유보금:** `read_reward_elastic_contingent_scope_liability_wei_v1`이 미완료 코호트 전체 2,127개를 예약하므로 공통 풀 전환 **직전**에 이중 예약을 해소해야 한다. 기존 지급 보장이나 실제 HELD 보상은 분리한다.
4. **과거 지급 경로:** `read_reward_boost_reserve_late_quote` 및 `commit_reward_reservation_with_late_reserve`의 과거 인용을 신규 Writer로 교체하되, 전환 이전 확정 지급 건은 변경하지 않는다.
5. **예상 보상 일치:** 화면 숫자와 서버의 실제 지급 견적이 동일한 공통 계산 규칙을 사용해야 한다. 문구와 UI는 수정하지 않는다.
6. **자동 이월 비활성화:** 별도 Source Sweep/Destination Top-up이 새 원장과 동시에 돈을 예약하지 않도록 전환 시 폐기 경로를 차단한다. 감사용 과거 원장은 보존한다.
7. **안전한 순서:** 미리보기 DB의 Production 스키마 차이 먼저 해소 → 실패/중복/동시 완료/X/회수오프셋 회귀 테스트 → 신규 Writer와 화면 배포 → 운영 DB 원자 전환 → 관측·롤백 검증.

## 현재 차단 조건
- Preview DB에는 Production의 `read_reward_elastic_contingent_scope_liability_wei_v1` 함수가 없어 결제 경로의 실사용 통합 테스트를 바로 할 수 없다.
- 이 함수와 확정 예산/DB 트리거를 동시에 우회하는 잘못된 배포는 잘못된 X 보상 또는 Claim 오류를 유발할 수 있으므로 **1단계는 지급 로직을 절대 활성화하지 않는다.**
