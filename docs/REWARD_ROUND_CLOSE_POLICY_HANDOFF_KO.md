# VeInvite 보상 정산 개선: 완료 라운드 균등 분배

## 사용자와 합의한 최종 정책
1. 온보딩 라운드가 아니라 **실제 마지막 미션(투표)을 완료한 라운드**를 기준으로 지급 대상을 묶는다. 데이터의 `invitations.vote_round_id`와 실제 `vote_completed_at`·온체인 투표 증명을 사용한다.
2. 해당 라운드가 공식 종료되고 데이터 최종성/시빌 판정이 끝나면, **그 라운드의 정상 완료자 수**로 지급 가능한 공유 보상 풀을 균등 분배하고 **한 번에 원자적으로 확정**한다. 하루 중 먼저 완료했는지 여부는 금액에 영향을 주지 않는다.
3. 미완료자의 몫은 미리 예약하지 않는다. 124라운드에 초대받았더라도 130라운드에 미션을 완료하면 130라운드 정상 완료자와 함께 계산한다.
4. `Claim` 클릭은 송금을 시작하는 행위일 뿐, 이미 확정된 금액을 재계산하지 않는다. 수령하지 않은 기본 보상은 다른 라운드 예산에서 차감·보호한다.
5. 보상 풀을 임의로 남겨두는 상한/이월 유보금은 추가하지 않는다. 지급 가능한 사용자 보상 풀을 활용하며 신규 할당은 다음 공식 입금 이후에만 반영한다.
6. **X 공유 10 B3TR**은 지급 가능액 산정 시 정상 완료자마다 보호하고, 유효한 기존 보너스·24시간 게시 및 유지 검증·중복 방지·지급 기록을 보존한다. 기존 운영비 20%를 중복 차감하지 않는다.
7. 시빌 판정·중복 보상·회수 상계·기존 확정 미지급 Claim 및 과거 라운드 지급 내역은 변경하지 않는다.
8. 홈 화면은 예상 금액 **한 개**만 보여준다. 새로 참여할 사용자 1명과 최근 활동 중인 기존 사용자를 감안해 예상 보상을 표시하되, 이 수치는 확정 지급 약속이 아니다. 실제 확정 금액은 사용자 개인 Claim UI에서 조회한다.

## 중요: 현행 동작과 새 정책 사이의 차이
2026-11-12 시점 Production DB에서 `shared_pool_settings.enabled=true`이다. 현재 `commit_reward_shared_pool_v1`은 **보상이 가능한 개별 완료자에게 즉시 금액을 확정**하며, `read_reward_reservation_candidates_v2` 전체 미확정 후보를 분모로 사용한다. **같은 투표 라운드가 끝날 때까지 기다렸다가 그 라운드 전체 완료자에게 동일 금액을 한 번에 확정하는 방식은 아직 아니다.**

이 문서가 작성된 시점에 위 개선안으로 실제 지급 시스템을 전환하거나 기존 예약을 수정하지 않았다. 새 화면 추정 로직만 별도의 코드 브랜치에서 준비한다.

## 후속 엔지니어링 — 반드시 지켜야 할 조건
- 새 기능은 기본적으로 꺼진 `round_close_settlement` 모드에서 시작한다. 활성화는 **앞으로 시작하는 아직 미지급 기록이 없는 라운드**에서만 허용한다. `reward_cohort_round_id`는 과거 재원/증빙 연결용으로 그대로 보존한다.
- 온체인 마지막 투표 `vote_round_id`·완료 블록·최종성, 공식 라운드 종료 영수증과 최종 Sybil CLEAR를 검증한다. 미완료자·차단자는 분모에서 제외하지만, 미션 완료 후 판정 대기 중인 사람의 몫을 다른 사람에게 먼저 주지 않도록 코호트 확정을 유예한다.
- 보상액은 `현재 물리적 풀 - 이미 확정된 미지급 기본/X 의무 - 새 완료자 수 × 10 X 예비금`을 **정상 완료자 수로 나눈 값**으로 책정한다. 양수의 반올림 잔액은 풀에 남기며 이중 보상에 쓰지 않는다.
- PostgreSQL 동일 트랜잭션과 공유 금융 advisory lock 안에서 대상자·금액을 재조회, N명 보상을 **전원 예약하거나 아무도 예약하지 않는** 방식을 채택한다. 어느 한 명이 실패하면 모두 롤백한다. Claim과 X 지급도 동일한 미지급 의무를 보게 한다.
- 새 라운드 활성화는 신·구 버전 혼합 지급을 명시적으로 막아야 한다. 이전에 확정된 보상과 정상 X 보너스를 환수·변경하지 않는다.
- 자금 부족, 미확정 Sybil, 완료 시점 경계, 동시 완료, 종료 직전/직후 완료, 수령 지연, 복구 재시도, X 공유 후 24시간 보너스, 추가 투표 할당 입금, 지급 후 잔액 재조회, 서버 중단 후 재진입을 DB 롤백 테스트와 통합 QA로 검증한다.
- 별도 유료 인프라/새로운 크론을 추가하지 않고 현행 보상 예약·Claim 재시도 경로를 재활용한다. 운영 전환 전 기존 감시 알림이 변경된 정산 대기를 오류로 간주하지 않도록 함께 업데이트한다.

## 화면 예상 보상 단계
- `activeSharedPoolForecast.ts`: 최근 7일 활성화·미션 진행 및 현재 라운드 완료 후보를 읽고 새 참여자 1명을 추가하여 풀을 나눈다. 과거 오래 미완료, 차단, 이미 지급된 사람은 예상 분모에서 제외한다.
- `/api/rewards/estimate`: 기존 공개 SHADOW 견적의 가용 재원과 X 예비금을 재사용해 참여형 예측값을 만든다. DB 조회 실패나 표본 초과 시 숫자를 부풀려 보여주지 않고 PENDING으로 처리한다.
- 홈 UI는 기존 다국어 문구와 숫자 하나만 유지한다. 이 단계는 공개 예상치만 바꾸며, 실제 지급 예약 Writer/Claim/X 원장을 수정하지 않는다.

**배포 게이트:** 현 단계에서 기존 Production/Claim/X에 영향을 주는 운영 데이터 변경은 금지. 독립된 Preview DB에서 신규 원자 정산 테스트가 끝나고 Vercel Production 접근 권한 및 최종 CI를 확인한 뒤에만 지급 방식을 활성화한다.
